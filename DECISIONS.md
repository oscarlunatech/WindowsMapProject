# Decisions

Short entries: what was chosen, what was rejected, why. Add one whenever a real fork in the road gets picked.

## 2026-08-23 — vcpkg in manifest mode, not vendored

Chose a local vcpkg install (`VCPKG_ROOT`) with `builtin-baseline` pinned in `vcpkg.json`, over vendoring vcpkg as a git submodule.

Would revisit if reproducibility across machines becomes a problem — the baseline pin should be enough, but a submodule guarantees the tool version too.

## 2026-08-23 — Ninja generator, requires a Developer shell

`CMakePresets.json` uses the Ninja generator rather than the Visual Studio generator, for fast incremental builds and CI parity (GitHub's `windows-latest` runners ship Ninja). The tradeoff: Ninja can't locate `cl.exe` on its own, so configuring/building must happen from a Developer Command Prompt/PowerShell (or after running `vcvars64.bat`) rather than a plain shell. CI will need `ilammy/msvc-dev-cmd` (or equivalent) before the CMake steps.

## 2026-08-23 — proj.db copied next to the executable, path set at runtime

PROJ doesn't discover `proj.db` next to the exe on Windows by default, and vcpkg's applocal DLL-copy step doesn't cover data files. Fixed by copying `proj.db` alongside the binary in a CMake post-build step, and pointing `PROJ_DATA` at the executable's own directory at startup (`CPLGetExecPath` + `CPLSetConfigOption`) — so it works with no environment setup on a clean machine, rather than relying on a `PROJ_DATA`/`PROJ_LIB` env var the user would have to remember to set.

## 2026-08-23 — golden-image test compares PNGs byte-for-byte, not with a tolerance

`test_render.cpp` requires the freshly rendered bitmap to exactly match the committed golden PNG, no per-pixel tolerance. This only works because rendering forces `D2D1_RENDER_TARGET_TYPE_SOFTWARE` (WARP), which should be deterministic regardless of the local GPU/driver.

Risk: this session only has one machine to test on, so cross-machine/CI determinism (different Windows or D2D versions producing slightly different antialiasing) is unverified. Chose exact matching anyway rather than building a tolerance-based comparison up front for a flakiness problem that hasn't actually been observed yet. Revisit with a per-pixel-tolerance + mismatch-percentage comparison if CI proves the exact match too brittle.

## 2026-08-23 — hand-rolled Douglas-Peucker instead of GEOS

`geom::simplify` (`Cartograph.Core/src/geom/simplify.cpp`) implements Ramer-Douglas-Peucker directly rather than calling GEOS (`geos::simplify::DouglasPeuckerSimplifier`), even though GEOS is already a dependency and is the project's designated geometry-algorithms library.

Douglas-Peucker is a simple, well-defined recursive algorithm over a flat point list, unit-tested directly against hand-computed expected output. That's a different category from the "never write your own datum math" rule for reprojection (Phase 6) — that rule is about subtle, hard-to-verify correctness (datum shifts, edge-of-domain behavior) where a wrong answer can look plausible. A wrong Douglas-Peucker implementation is easy to catch with a handful of known-distance test cases, which `test_simplify.cpp` does. Would revisit if the outline's later geometry work (buffer, intersect, validity) needs GEOS integration anyway, at which point routing simplification through GEOS too might reduce total surface area rather than add it.

## 2026-08-23 — Viewport fills the window by expanding the extent, not letterboxing

`render::Viewport` used to preserve aspect ratio by uniform-scaling to the limiting axis and centering the result, leaving blank letterbox/pillarbox bars whenever the window's aspect ratio didn't match `mapExtent`'s. Changed it to instead grow `mapExtent` about its own center along whichever axis is narrower, so the map always fills the entire screen at the same uniform scale.

Two alternatives considered and rejected:
- **Crop ("cover")**: scale to the *larger* of scaleX/scaleY and let the render target clip the overflow. Fills the window with no distortion, but permanently hides map content at the edges on whichever axis is over-full — bad for a viewer whose job is showing data.
- **Stretch (non-uniform scale)**: independent X/Y scale factors so the map exactly fills the window with zero blank space. Rejected because it visibly distorts geometry (a square county renders as a rectangle), which conflicts with the "correct before fast" design goal — this is a geometric distortion, not just a display convenience.

Expanding the extent was chosen because it never hides or distorts data, matches the resize behavior of existing desktop GIS viewers (QGIS, ArcMap), and is a small, self-contained change in `Viewport`'s constructor — `Viewer` still just rebuilds a `Viewport` fresh every frame from its own `mapExtent_`, unchanged. `Viewport::mapExtent()` now returns the displayed extent rather than the exact one passed in, which callers should be aware of. The golden-image test (`test_render.cpp`) was unaffected since its fixture's bbox and screen size already share an exact 2:1 aspect ratio, so the expansion is a no-op there.

## 2026-08-23 — Phase 4 optimizations only touch the live Viewer, not Renderer::render

`SpatialIndex`/`LayerCache`/`drawDatasetCulled` are wired into `Viewer` (`src/viewer.cpp`) and the `bench` CLI subcommand, but `Renderer::render` (the off-screen, golden-image-tested path) still calls the original, unculled `drawDataset` unchanged.

Deliberate: the performance problem Phase 4 solves is specifically live pan/zoom frame time, not one-shot file rendering, and leaving `Renderer::render` untouched meant the Phase 2 golden-image test needed zero changes or re-baselining through this entire phase (verified: `test_render.cpp` passed unmodified before, during, and after all Phase 4 work). If a future phase wants a culled/batched off-screen render path (e.g. for faster large-area exports), it should reuse `drawDatasetCulled` directly rather than growing `Renderer::render` a mode flag.

## 2026-08-23 — Phase 5 threading: one jobs::ThreadPool, message-post handoff, D2D stays single-threaded

Phase 5 covers three things the user asked for together: background dataset loading (`Viewer` used to call `Dataset::open()` synchronously before the window even existed), off-main-thread rendering, and parallelizing `drawDatasetCulled`'s per-layer work. All three share one new `jobs::ThreadPool` (`Cartograph.Core/include/cartograph/jobs/thread_pool.h`) - a plain fixed-size mutex+condvar pool, no separate parallel-for abstraction, since every caller just does its own submit-loop/collect-loop.

**D2D stays confined to its owning thread.** Both `ID2D1Factory`s in this codebase (`Viewer::createDeviceResources`, `OffscreenTarget`) are `D2D1_FACTORY_TYPE_SINGLE_THREADED`, so no D2D call may happen off the thread that created the factory. Rather than switching to `D2D1_FACTORY_TYPE_MULTI_THREADED`, `drawDatasetCulled` (`renderer.cpp`) is split into a parallel phase (R-tree query + simplification-bucket lookup + `viewport.mapToScreen` coordinate transform, producing plain `D2D1_POINT_2F` data - no D2D objects touched) and a serial phase (the actual `ID2D1PathGeometry` sink-writing and `DrawGeometry`/`FillGeometry` calls) that runs back on the caller's thread. `drawDataset`/`Renderer::render` (the golden-image path) are untouched, continuing the Phase 4 precedent above - `test_render.cpp` needed zero changes.

**No nested pool submission.** A task submitted to the pool must never itself submit-and-wait on the same pool - with a fixed worker count that can starve/deadlock. `Viewer`'s background loader runs on its own dedicated `std::thread` (not a pool worker) and uses `pool_` from there as an ordinary client; the UI thread does the same per-frame in `onPaint`. Neither is ever called from inside a pool task.

**Background load handoff uses PostMessage, not a mutex.** `Viewer::loadInBackground` (on `loaderThread_`) builds a heap-allocated result (`Dataset` + `LayerCache`s + extent, or an error message) and posts it to the window via `PostMessageW`/a custom `WM_APP` message. `dataset_`/`layerCaches_`/`mapExtent_`/`loadState_` are then written exclusively by the UI thread inside `handleMessage`, once it takes ownership of the pointer - no lock needed anywhere, because Win32's message queue is itself the cross-thread synchronization point.

**Chunk per-frame parallel work by worker count, not by layer.** The first version submitted one pool task per layer (~20/frame for the NJ roads dataset). That measured as a net *regression* in the Debug build (avg frame time roughly 4x worse than pre-Phase-5) - the fixed cost of a heap-allocated `packaged_task` plus a mutex lock and a condition-variable wake, ~20 times a frame at 60fps, is larger than the work being parallelized once you're in an unoptimized (`/Od`, `/RTC1`, debug CRT) build. Fixed by chunking into at most `pool.size()` tasks, each covering a contiguous range of layers, writing into disjoint slices of one preallocated result vector (no lock needed - the ranges never overlap). This is a real, if more modest, win in Release (~25-30% faster than the Phase 4 numbers on the same dataset/camera path; see `BENCHMARKS.md`); Debug is still measurably slower than pre-Phase-5 due to inherent synchronization-primitive overhead in an unoptimized build. **Benchmark this project in Release** (`cmake --preset x64-release`) - the Debug preset remains the documented day-to-day dev workflow, but its numbers are not representative of real per-frame cost once threading is involved.

**Trap worth recording:** `ThreadPool`'s constructor originally had `std::size_t threadCount = std::max(1u, std::thread::hardware_concurrency())` as a default argument. Any translation unit that includes both `windows.h` (without `NOMINMAX`, which nothing in this project defines) and `thread_pool.h` - which now happens everywhere `renderer.h` is included, since it needs `jobs::ThreadPool` for `drawDatasetCulled`'s new parameter - had `std::max`/`std::min` silently mangled by windows.h's function-like `max`/`min` macros. This didn't fail as an ordinary compile error; it corrupted the parser badly enough to crash `cl.exe` (a genuine access-violation ICE) with diagnostics pointing at completely unrelated, unmodified code elsewhere in the same translation unit - very confusing to debug, since it looked exactly like toolchain/environment corruption (and an actually-corrupted shared PDB from an unrelated crashed `mspdbsrv.exe` earlier in the same session made that red herring even more convincing). Fixed by parenthesizing every `std::min`/`std::max` call reachable from a `windows.h`-including TU: `(std::min)(a, b)`. Worth remembering for any future `std::min`/`std::max` added near Win32 code in this codebase.

**Follow-up (same day): parallelize ID2D1PathGeometry construction, not just the coordinate math.** Per-core CPU profiling of the above in the live `Viewer` (Debug) showed only one core busy - the initial split only parallelized query/simplify/coordinate-transform (`prepareLayer` returning plain point data), leaving the actual `ID2D1PathGeometry` sink-writing (`BeginFigure`/`AddLine` per point) serial, and for this dataset's dense line geometry that serial phase dominates frame time (Amdahl's law caps the win regardless of how well the smaller parallel phase scales). Fixed by having `prepareLayer` build the `ID2D1PathGeometry` itself on the pool worker, switching both D2D factories (`Viewer`'s and `OffscreenTarget`'s) from `D2D1_FACTORY_TYPE_SINGLE_THREADED` to `D2D1_FACTORY_TYPE_MULTI_THREADED` to make that safe. `ID2D1RenderTarget` itself is thread-affine regardless of factory type, so `DrawGeometry`/`FillGeometry`/`FillEllipse` still only run on the caller's thread in `drawDatasetCulled`'s (now shorter) serial phase 2. Verified `test_render.cpp`'s golden-image comparison is still byte-exact after the factory type change (expected - it doesn't touch rendering output, only call-site threading safety). Result: a further ~12% improvement in Release (~36% faster than the pre-Phase-5 baseline overall, see `BENCHMARKS.md`) but not dramatic - `D2D1_FACTORY_TYPE_MULTI_THREADED` makes concurrent resource creation *safe* via its own internal locking, not necessarily highly parallel, so there's a ceiling here that isn't fully understood/explored. Debug saw no meaningful change. Worth revisiting if per-frame cost matters more later - candidates would be profiling where D2D's internal lock contention actually falls, or reducing per-frame geometry-object churn (e.g. reusing buffers across frames) rather than parallelizing further.

## 2026-08-23 — Phase 6 reprojection: normalize every layer to EPSG:4326 at load time, via a new crs:: module wrapping PROJ directly

Scoped with the user to: every layer gets reprojected to one fixed target CRS (`EPSG:4326`) inside `Dataset::open()`, rather than a user-selectable display CRS or a fix scoped to one dataset pair. `EPSG:4326` specifically because the golden-image fixture (`ne_110m_admin_0_countries.shp`) is already in it, keeping that identity case byte-exact with no re-baselining.

**New `crs::Transformer`** (`Cartograph.Core/include/cartograph/crs/transformer.h`, `src/crs/transformer.cpp`) wraps PROJ's C API (`proj.h`) directly rather than going through GDAL's `OGRCoordinateTransformation` - this is the "never write your own datum math" rule from the Phase 3 entry, and matches `README.md`'s architecture line, which had earmarked a `crs/` module since before this phase existed. Hidden behind a pimpl, same pattern as `index::SpatialIndex` hiding `boost::geometry::index::rtree` - `proj.h` never appears in a public header, `PROJ::proj` is linked `PRIVATE`.

Wired into `dataset.cpp` (still the only file allowed to touch GDAL/OGR headers - `crs::Transformer` only touches PROJ, not GDAL): `convertLayer` builds one `Transformer` per layer from its CRS to `EPSG:4326` (skipped entirely if the layer has no CRS metadata - there's no legitimate source to transform from), and every point extracted from OGR is transformed as it's read. The layer's stored extent is now computed by unioning each converted feature's `Geometry::extent()` rather than trusting `ogrLayer.GetExtent()`'s native-CRS bbox, which would be wrong post-transform. `Layer::crsWkt()` now reports the *actual* CRS the coordinates are in (`EPSG:4326` if transformed, empty if unknown) rather than the source file's original CRS - the two would otherwise silently disagree.

Three traps hit along the way, each worth remembering for future CRS-adjacent work:

1. **Feed PROJ WKT2, not GDAL's default WKT1 pretty-print.** Shapefile `.prj` sidecars are very often ESRI-flavored WKT1 (e.g. `GCS_WGS_1984`/`D_WGS_1984` naming) - GDAL's `OGRSpatialReference` parses that dialect fine, but raw PROJ's `proj_create()` rejected it outright (`"unrecognized format / unknown name"`) when fed the fixture's exact `.prj` content in a unit test. Fixed by exporting via `srs->exportToWkt({"FORMAT=WKT2", nullptr})` instead of `exportToPrettyWkt()` - WKT2 is PROJ's own native, unambiguous format and round-trips cleanly regardless of the source file's original WKT1 dialect.
2. **`proj_create_crs_to_crs`'s result needs `proj_normalize_for_visualization`.** Without it, the built transform uses each CRS's authority-defined axis order, which for some CRSs is lat/lon rather than the conventional GIS lon/lat/x/y - a silent axis-swap bug for exactly the CRSs where it'd be hardest to notice by eye. This is PROJ's own documented fix, applied unconditionally to every non-identity transform.
3. **A missing NADCON/NTv2 datum-shift grid degrades gracefully, not loudly.** This vcpkg PROJ install has no grid files for the specific NAD83→WGS84 (EPSG:4269→4326) operation the real NJ roads dataset needs - PROJ's "best" pipeline for that pair needs a `hgridshift` step it can't find, and (per PROJ's own documented behavior for a missing grid within an otherwise-valid pipeline) silently treats that step as identity rather than failing the whole transform. Verified via a direct unit test (`test_crs_transformer.cpp`) that the result is a plain, finite passthrough - not NaN/garbage, and not silently treated as some other CRS - and that this specific pair's true datum shift is a well-known, negligible ~1-2m in CONUS. Accepted as-is for this phase rather than pursuing `proj_context_set_enable_network` (needs runtime internet access) or bundling grid files (adds distribution weight) - revisit if a dataset needing a *larger* unavailable grid shift is ever encountered. The one real fix applied: PROJ prints this warning through its own logging on every single point transformed by default, which is both noisy and a real per-point performance cost at dataset scale - `crs::Transformer` sets `proj_log_level(ctx, PJ_LOG_NONE)` on its own context, since real failures are already surfaced as `CrsError` via explicit return-value checks rather than needing PROJ's own log output.

`Transformer`'s construction also checks `proj_is_equivalent_to(source, target, PJ_COMP_EQUIVALENT)` **before** building any transform pipeline, short-circuiting to a pure passthrough (`isIdentity() == true`) when source and target are equivalent CRSs. This - not merely trusting PROJ's pipeline to numerically no-op on a technically-different-but-equivalent WKT string - is what keeps the golden-image fixture bit-for-bit unchanged (verified: `test_render.cpp` passed unmodified after this phase).

## 2026-08-24 — Phase 7 symbology: single/categorized/graduated renderers, resolved once per dataset rather than per frame

Scoped with the user to three things: the standard GIS renderer trio (single symbol, categorized on an attribute's unique values, graduated on a numeric attribute's ranges); a JSON style file supplied via a new `--style` flag on `render`/`view`/`bench`, since with no WPF shell yet the CLI is the only user-facing surface; and built-in defaults that keep the golden-image test byte-exact rather than re-baselining it. Labels were explicitly considered and left out - they need DirectWrite plus a placement/collision problem that's its own phase.

New `style::` module (`Cartograph.Core/include/cartograph/style/`), three headers: `symbol.h` (the `Color`/`Symbol` value types), `style_spec.h` (the dataset-independent `StyleSpec` parsed from JSON, plus `StyleError`) and `stylesheet.h` (a `StyleSpec` bound to a concrete `Dataset`).

**`Symbol` carries all three geometry classes at once** (polygon fill + outline, line stroke, point fill/radius) rather than one generic fill/stroke pair. Two reasons: it has to be able to express the pre-Phase-7 hardcoded styling exactly, which used *different* colors per geometry class (gray polygons, black outlines, blue lines, red points); and `drawDatasetCulled` already batches a layer's points, lines and polygons into separate draw calls, so it wants all three in hand anyway. `Symbol`'s default member initializers *are* the old hardcoded values, which is what makes `Stylesheet::defaults()` byte-exact - verified two ways: `test_render.cpp` passed unmodified, and `cartograph_cli render` with no `--style` produces a PNG whose SHA-256 equals the committed golden's.

**`Stylesheet` resolves every feature's symbol once, at construction, into a flat `[layer][feature] -> symbol index` table** rather than evaluating the renderer per feature per frame. A categorized renderer otherwise costs a string comparison per visible feature per frame, and a graduated one a break search, for an answer that provably cannot change - features are immutable once `Dataset::open()` returns. This is the same bargain `LayerCache` already makes for simplification, and it keeps the per-frame cost of symbology down to an array index. It's also why `drawDatasetCulled` takes the stylesheet as a **required** parameter rather than defaulting one: like `layerCaches`, it's built once when the dataset loads (`Viewer` does it on `loaderThread_`, `bench` before the timed loop) and passed unchanged every frame. `drawDataset`/`Renderer::render` - the one-shot paths - do get convenience overloads that build a default stylesheet per call, which is what lets `test_render.cpp` keep calling `Renderer::render(dataset, viewport)` untouched.

**Kept separate from `LayerCache` rather than folded into it.** Both are "precomputed once per dataset, read every frame," so merging them was tempting. Rejected because a `LayerCache` (R-tree + simplification buckets) is style-independent: restyling must not invalidate the spatial index, and swapping datasets must not silently reuse a stale style. Two objects with independent lifetimes says that; one object doesn't.

**Batching is now per (layer, symbol), not per layer.** This is the one real interaction with Phase 4's central optimization. Batching a whole layer into one `ID2D1PathGeometry` is only valid when every feature in it draws the same - with a categorized renderer they don't. `prepareLayer` now buckets a layer's visible features by resolved symbol and emits one batched geometry per non-empty bucket per geometry class. A single-symbol layer collapses to exactly one bucket and is bit-identical to Phase 4's behavior; a categorized layer costs one batch per category *actually on screen*, never one per feature. Buckets are a flat `vector` indexed by symbol rather than a map, since `Stylesheet` dedupes symbols by value and the resulting tables are tiny - that also makes draw order deterministic (ascending symbol index).

Measured rather than assumed, because splitting one large geometry into several smaller ones could plausibly have cost draw calls: on the NJ roads dataset in Release, single-symbol is unchanged from Phase 5 (~105ms vs 103.90ms avg, inside run-to-run noise), and a 7-symbol categorized style at a *controlled* uniform stroke width is ~98ms - slightly **faster**, not slower. Going from ~21 to ~147 draw calls per frame is still trivially few, and the smaller per-batch geometries appear to be cheaper for D2D to build than one enormous one. See `BENCHMARKS.md` for the full table, including why the first categorized measurement was confounded (varied stroke widths change rasterizer coverage, so it wasn't measuring batching at all).

**Brushes are created once per frame for the whole symbol table**, not per batch - `ID2D1SolidColorBrush` is a render-target resource and so is one of the few things that still can't move to a pool worker. Symbol tables are deduplicated and small, so this stays about as cheap as the four fixed brushes it replaces.

**Errors are loud: an unknown layer name, field name, symbol key or top-level key throws `StyleError`** rather than falling back to the default. A style file is hand-written, and a silently-ignored `"linewidth"` typo is indistinguishable from the renderer being broken; the messages list what *was* available. Same reasoning applies to `Graduated`'s breaks, which resolution walks in order taking the first whose `max` the value doesn't exceed - an unsorted list would silently misclassify rather than fail, so ascending order is enforced at parse time.

**`nlohmann-json` added to `vcpkg.json`, linked `PRIVATE`** and confined to `src/style/style_io.cpp` - `style_spec.h` exposes only Cartograph's own types. Same containment pattern as boost behind `index::SpatialIndex` and PROJ behind `crs::Transformer`, though this one needs no pimpl since the JSON types never reach a member declaration.

**Incidental fix:** `CLAUDE.md` and `README.md` both referenced a "Phases section" and a test-data tier table in `README.md` that had never actually been written. Both now exist.

## 2026-08-24 — Scope change: from read-only viewer to a complete GIS at 1.0

Decided with the user immediately after Phase 7. The project's stated goal was "a viewer with identify and basic symbology. Not an editor, not a geoprocessing suite," with web services and format writing explicitly out of scope. That is now replaced: **1.0 is a GIS that does a complete workflow** — open, project, style, label, identify, edit, analyze, export. Phases 8–21 in `README.md` are the plan.

Four pillars were added, all four chosen by the user: raster support, editing/digitizing, a GEOS analysis toolbox, and web basemaps. Three of the four directly contradict a line that used to be in the out-of-scope list, which is the point of writing this entry rather than quietly editing the README.

**The realism constraint, and how it was resolved.** The user asked for this "in a realistic manner" and picked a ~14-phase horizon, but also picked all four pillars — and web basemaps had been presented as belonging to the *longer* (~25-phase) option. Rather than pretend all four fit at full depth, each pillar is scoped to a deliberately thin but genuinely finished slice, written into README as a pillar table so "fully functional" is checkable rather than aspirational: raster display but no band math, editing with undo but no topology, the core overlay/proximity ops but no graphical modeler, XYZ tiles but no WMS/WFS. The things cut are listed as *deferred*, not rejected, and separated in the README from the permanent non-goals (cross-platform, 3D, network analysis, plugin host), which are unchanged.

**Ordering: Core-first, shell at Phase 12–14, not Phase 8.** The alternative considered was standing up `Cartograph.Interop` and the WPF window immediately, for visible progress and early exposure of interop problems. Rejected: the model still has to grow multi-layer support (Phase 9), a selectable display CRS (Phase 10) and a non-vector data path (Phase 11), and building a shell against a single-dataset, single-CRS, vector-only model means reworking the UI underneath itself three times. Phases 1–7 demonstrated that hard problems are cheap to get right in a Core with no window; the same reasoning applies to the model work. Cost accepted: no GUI for four more phases.

**Two consequences worth recording now, before they bite:**

1. **Editing invalidates assumptions two existing caches depend on.** Phase 7's `Stylesheet` precomputes every feature's symbol at construction, and `LayerCache` precomputes an R-tree and simplification buckets, both justified by features being immutable after `Dataset::open()` returns. That justification dies with editing. Phase 16 ("mutable data model + cache invalidation") exists purely so this is a deliberate phase with its own tests rather than something discovered midway through building digitizing tools. Do not start Phase 17 before it.
2. **Phase 10 revisits Phase 6's central decision.** Phase 6 normalizes every layer to `EPSG:4326` at load time, chosen partly because the golden-image fixture is already in it, keeping that test byte-exact. A user-selectable display CRS makes 4326 one option rather than the target. Keeping 4326 available as an explicit choice is what should preserve the golden-image test — worth verifying early in that phase rather than at the end.

Also: there is still **no CI**, which the Phase 1 entry anticipated ("CI will need `ilammy/msvc-dev-cmd`"). That mattered less for a read-only viewer with one committed fixture. With editing, persistence and analysis coming, and with the golden-image test's cross-machine determinism still documented as unverified, it matters more. Not assigned a phase number yet; should be picked up opportunistically rather than deferred to 1.0.

## 2026-08-24 — Phase 8 identify: hand-rolled predicates, and the R-tree narrows but never decides

Two new modules: `geom::predicates` (`geom/predicates.h`, joining `geom::simplify`) and `query::identify` (`query/identify.h`). Plus an `identify` CLI subcommand and click-to-identify in the live `Viewer`.

**One primitive, not a hit-test zoo.** `geom::distanceTo(geometry, point)` returns a distance in map units — exactly `0` when the point is inside a polygon (holes respected), infinity for empty/Unknown geometry. Every hit test is then just `distanceTo(...) <= tolerance`, which collapses "is it inside", "is it near", and "which is nearest" into one function with one set of tests. Returning infinity rather than, say, a sentinel or an optional is what guarantees degenerate geometry can never register a hit no matter how large the caller's tolerance.

**Hand-rolled rather than GEOS or Boost.Geometry.** Ray-casting point-in-polygon and point-to-segment distance are both in the category the Phase 4 `geom::simplify` entry called out as fine to write directly: simple, well-defined, and verifiable against hand-computed cases (`test_predicates.cpp` does exactly that). Two other considerations pushed the same way. GEOS is a dependency but has never been included or linked, and Phase 19 is where it's scheduled to arrive with its own decisions about conversion and lifetime — pulling it forward for ~60 lines of arithmetic would spend that phase's design budget early. Boost.Geometry is already linked, but only `PRIVATE` behind `SpatialIndex`'s pimpl, and using its predicates would mean converting every candidate `Geometry` into boost types on every click — real work to avoid arithmetic that's cheaper than the conversion. Revisit if Phase 19's GEOS integration makes routing these through it *reduce* total surface area rather than add it, which is the same escape hatch the simplify entry left open.

**The R-tree narrows candidates; it never decides.** `identify` queries each `LayerCache`'s index with a tolerance-sized box around the point, then runs the exact `distanceTo` test on every candidate that comes back. An overlapping bounding box says very little about the geometry inside it — Norway's extent covers a large area of open sea because of Svalbard and the fjords, and a click there must not report Norway. That's a named test (`identify uses exact geometry, not the feature's bounding box`) specifically so the exact test can't be optimized away later on the theory that the index already answered the question.

**Identify tests the original geometry, not `LayerCache`'s simplified copy.** The renderer draws zoom-appropriate simplified geometry; identify deliberately reaches past that to `layer.features()[i].geometry()`. Identify should answer about the data, not about what the current zoom rounded it to — otherwise the same click would report different results at different zoom levels, which is exactly the sort of thing that's maddening to debug later.

**Ordering is topmost-layer-first, then nearest-first.** Later layers draw over earlier ones, so the highest layer index is what's actually visible under the cursor and belongs at the top of the result list. Ties break on feature index purely so the output is deterministic.

**Tolerance is map units in Core, pixels at the edges.** A click target is naturally a pixel radius, but Core has no screen, so `identify` takes map units and callers convert. `Viewer` divides a 5px radius by `viewport.scale()` per click, so the target stays 5px at every zoom rather than being enormous zoomed out and unusable zoomed in. The CLI has no viewport at all, so it defaults to 0.1% of the dataset extent's diagonal — the same data-scaled trick `LayerCache` uses to pick simplification buckets.

**Click vs. drag in `Viewer`.** Left-drag already panned, so identify needed to not fire on every pan. `WM_LBUTTONUP` treats the gesture as a click only if the pointer never travelled more than 4px; below that threshold `onMouseMove` also suppresses panning outright, so a click doesn't nudge the map by a pixel or two of hand-shake. Once the threshold is crossed the pan applies the *full* delta from the button-down point, so no motion is lost to the dead zone.

Verified in the live window by posting a synthetic `WM_LBUTTONDOWN`/`WM_LBUTTONUP` pair at a known client coordinate over central Africa and screenshotting the result: the overlay reported Democratic Republic of the Congo. Worth recording that `PostMessage` reaches the window regardless of focus or occlusion, but `CopyFromScreen` captures *screen* pixels — the first attempt screenshotted an unrelated window sitting on top, so the window has to be brought to the front before any screen capture.

## 2026-08-25 — Phase 9: a Map is the thing that gets drawn; Dataset is demoted to loader

`Map` and `MapLayer` (`cartograph/map.h`) replace "one `Dataset` per run". A `Map` is an ordered stack of layers gathered from one or more files, drawn bottom-to-top; `Map::open(paths)` opens each path and appends its layers, so stack order follows argument order. `Dataset` keeps the GDAL boundary and the reprojection but is now purely the loader - `takeLayers()` moves its layers into a Map and nothing holds a Dataset afterwards. `drawDataset`/`drawDatasetCulled` became `drawMap`/`drawMapCulled`, and `Renderer::render`, `style::Stylesheet` and `query::identify` all now bind to a Map.

**The LayerCache moved *into* MapLayer**, rather than staying a `vector<LayerCache>` passed alongside. It's derived from that layer's geometry, so the two are invalidated by exactly the same events - which is precisely what Phase 16 (mutable data) will need, and which a parallel vector makes easy to get wrong. This also deleted a whole class of bug: `drawDatasetCulled` used to defensively `min()` the dataset's layer count against the cache vector's, because nothing structurally guaranteed they matched. Now they can't disagree.

**Styling deliberately did *not* move in.** A `Stylesheet` still binds to the whole Map rather than living per-layer, preserving the Phase 7 split: restyling must not invalidate an R-tree, and rebuilding an R-tree must not discard styling. Two things derived from a layer, with genuinely different lifetimes, so only the one that shares the layer's lifetime got absorbed.

**Layer opacity uses `ID2D1Brush::SetOpacity`, not `PushLayer`.** Pushing an `ID2D1Layer` per map layer would give true group opacity - overlapping features within one layer compositing as a single unit - at the cost of an intermediate surface per layer, which on the 21-layer NJ dataset is a lot to pay every frame. Setting brush opacity for the duration of a layer composites each feature separately instead. The two differ only where features *inside the same layer* overlap each other, which for this viewer's layer stacks is a good trade. Recorded rather than assumed, so if a use case ever needs the exact semantics the alternative is already written down.

**Hidden layers cost nothing.** The visibility check sits in the parallel phase of `drawMapCulled`, before any R-tree query or geometry construction, and `identify` skips hidden layers outright - clicking something you can't see shouldn't report a hit.

**`info` and `dump` still take the `Dataset` path, not the `Map` path.** They read names, fields and attributes and never draw or hit-test anything; building a Map would also build every layer's R-tree and simplification buckets, which is a lot of work to print a field list. That's the concrete reason `Dataset` stays a public type rather than becoming an implementation detail of `Map`.

**Styles match on layer name, so identically-named layers share a style.** With one file that was unambiguous; with N files two layers can collide. Left as-is deliberately: it's the desirable behaviour for something like 21 identically-shaped TIGER county road layers, and the style file's `default` key already covers the general case. Revisit if per-layer-instance styling is ever needed - the natural key would be layer index or source-path + name.

**A test assumption that was wrong, worth remembering:** the first version of the visibility test asserted that rendering one layer produced exactly the same count of pure-green pixels as rendering two identical stacked layers. It failed, 23264 vs 23706. Drawing the same geometry twice is **not idempotent under antialiasing** - a partially covered edge pixel blended twice lands closer to the pure fill colour than one blended once, so the two-layer render has ~2% more exactly-green pixels. Interiors are identical; only antialiased edges differ. The test now checks the same order of magnitude rather than exact equality. Any future pixel-counting test over stacked layers needs the same care.

Verified: golden image byte-exact (`Renderer::render` now takes a Map, and a one-layer Map renders identically to the old one-Dataset path); three separate NJ county shapefiles rendered as one correctly co-registered map with per-county styling; `identify` across a two-file stack reports the topmost layer first; and click-to-identify works in the live viewer over a three-file map. Release benchmark ~95ms avg on the 21-layer NJ dataset, versus ~105ms at Phase 7 - no regression.


**A trap in the synthetic click test harness, not in the product:** `WM_LBUTTONDOWN` makes `Viewer` call `SetCapture`, which routes *all* subsequent physical mouse movement to that window. If the real cursor is parked somewhere else while a synthetic click is posted, the first genuine `WM_MOUSEMOVE` reports a position far from the synthetic press point, and the viewer correctly reads that as a drag - so the map pans and no identify fires. The fix is to `SetCursorPos` onto the target first, so the synthetic gesture matches what real hardware would produce. A real user's cursor is always already at the press point, so this never affects them.

## 2026-08-25 — Phase 10: EPSG:3857 by default, and PROJ does not clamp

The display CRS is now selectable (`--crs`, `Map::open(paths, crs)`, `Map::displayCrs()`), defaulting to **EPSG:3857** rather than Phase 6's hardcoded EPSG:4326. Web Mercator because it's what web maps and XYZ basemap tiles use, which Phase 20 will need, and because plate carrée is a poor default for looking at anything but the whole world.

**The golden-image constraint resolved exactly as predicted, and checking it first was worth it.** `CLAUDE.md` recorded that Phase 10 would reopen Phase 6's decision and that verification belonged at the *start* of the phase. It did: `test_render.cpp` now opens with `"EPSG:4326"` explicitly, `crs::Transformer` short-circuits equivalent CRSs to an exact identity, and the comparison stayed byte-exact with no re-baselining. Three other tests failed on the default change and needed the same one-line pin — they use degree coordinates (`--bbox -180,-90,180,90`, lon/lat identify probes) which silently mean something else in metres. That's now written into the constraint list as the general rule.

**PROJ does not clamp, and this is the load-bearing finding of the phase.** Measured before designing anything: `EPSG:4326` latitude −90 into `EPSG:3857` returns y = **−242,529,000**, twelve times the projection's own −20,037,508 bound — and *finite*, so no error is raised and no NaN check would catch it. The Natural Earth countries fixture reaches −90 via Antarctica, so a naive Web Mercator default would have inflated the map extent 12× and rendered the world as an unusable sliver, with nothing anywhere reporting a problem.

Fixed by giving `Transformer` an **area-of-use clamp**: it asks PROJ for the target CRS's declared area of use (`proj_get_area_of_use`, in degrees), walks that box's perimeter through a WGS84→target transform to get the equivalent box in target coordinates, and clamps every transformed point into it. `targetBounds()` exposes the box and is invalid for identity transforms, which clamp nothing — that's what keeps the 4326 path bit-exact.

Three details worth keeping:
- **The perimeter is sampled, not just cornered.** Projected edges bow; for a conic or transverse-Mercator target the extreme easting can fall in the middle of an edge rather than at a corner, and four corners alone would clip real data. 32 samples per side, once per Transformer.
- **PROJ reports the EPSG registry's rounded ±85.06°**, not the exact ±85.0511288° that makes the Web Mercator world square. Near the pole a degree is ~1,276 km of northing, so that 0.0089° rounding puts the bound at ~20,048,966 instead of 20,037,508 — 0.06% past the canonical square. Deliberately not corrected: the clamp's job is to stop a 12× blowup, not to reproduce a constant. Tests assert it loosely so a future PROJ update refining the registry value doesn't break them.
- **Blanket clamping is the right call for a *display* CRS but not obviously for every CRS.** Data outside a projection's declared validity has no meaningful representation in it, which is why this is safe for 3857. For a narrow CRS (a single UTM zone, a state plane) clamping squashes out-of-zone data onto the zone boundary, where letting it extrapolate a little would look better. Accepted for now because the display CRS is exactly the case being solved; revisit if someone works habitually in a narrow projected CRS.

**`setDisplayCrs` re-reads every source file rather than transforming in place.** Layers are stored already-projected, so a second transform would have to compose new ← current ← source and accumulate error across repeated switches; keeping a pristine source copy alongside would instead double the memory of a 500k-feature map. Re-reading costs I/O on a rare, user-initiated action and always produces exactly what opening in that CRS would have. It's strongly exception-safe (the replacement is built fully before anything is swapped in — there's a test for a bogus CRS leaving the map untouched) and carries per-layer visibility and opacity across.

**A bug that bit during the phase, caught by its own test:** the first version of `setDisplayCrs` recovered the paths to re-read by de-duplicating consecutive `MapLayer::sourcePath()` values, reasoning that several layers usually share one dataset. That silently collapses the legitimate case of the *same file opened twice on purpose* — a map built from `[countries.shp, countries.shp]` came back with one layer instead of two. `Map` now stores the paths it was opened with, duplicates preserved. Deriving state that was given to you is a false economy.

**`bench` defaults to EPSG:4326**, alone among the commands, so its numbers stay comparable with everything already in `BENCHMARKS.md` — reprojecting the dataset changes what's being measured. `buildCameraPath` still writes its Newark target as lon/lat (that's how a reader can tell where it is) and transforms it into whatever CRS the map is in, so `bench --crs` aims at the right place instead of a point 74 metres from the origin.

Measured after: ~97ms avg in 4326 versus ~95ms at Phase 9 (noise), ~100ms in 3857. Per-frame cost is CRS-independent, as expected — reprojection happens once at load, not per frame.

## 2026-08-26 — Phase 11 raster: a source that stays open, and GDAL's warper repeats the pole trap

`raster::RasterSource` (`cartograph/raster/raster_source.h`) is the first non-vector data path. `MapLayer` became a `variant` of vector-or-raster content so both share one ordered stack - draw order has to interleave (a basemap under the vectors, an overlay over them) and two parallel lists can express neither. `query::identify` reports per-band pixel values for raster layers, the style file grew a `"type": "raster"`, and every command takes rasters and vectors interchangeably: `addPath` tries each path as vector first and as raster if that fails, so nothing has to declare which a file is.

Scoped with the user: sharp re-reads over a simpler one-shot load, style-file configuration over CLI flags, and raster identify in rather than deferred.

**A RasterSource keeps its GDAL handle open, unlike Dataset.** The Phase 1 rule - convert everything on ingest, close GDAL before returning, let no OGR pointer survive - is right for vector and impossible for raster here, because the whole point of this phase is re-reading the visible window whenever the view moves. There is no single "load it all" moment to close after. So the invariant is now narrower but still explicit: **exactly two translation units include GDAL headers** (`dataset.cpp` and `raster/raster_source.cpp`), both hide it entirely from public headers, and both call the new shared `detail::ensureGdalPlatformSetup()` rather than initialising GDAL themselves - either can be the first thing a process touches, and the raster path initially missed the `PROJ_DATA` setup that had been living inside `dataset.cpp`.

**`GDALAutoCreateWarpedVRT` reproduces Phase 10's pole bug, and worse.** It derives its output extent by transforming the source's corners itself, which never goes through `crs::Transformer` and so never sees that class's area-of-use clamp. Warping the 10800x5400 Natural Earth world raster into EPSG:3857 gave an extent running to +/-242,000,000 - and because the output *grid* is then sized to cover that, a 1119x12023 sliver: a tenth of the source's resolution, almost all of it empty polar stretch. Replaced with an explicit grid: sample the source extent's perimeter through `crs::Transformer` (which clamps), size square pixels to preserve roughly the source's pixel count, and call `GDALCreateWarpedVRT` with that geotransform. Same 64-sample perimeter walk as the vector clamp, for the same reason - projected edges bow, so the extreme easting can fall mid-edge. Result: 7635x7639, extent +/-20,048,966, correct. Worth remembering that `GDALCreateWarpedVRT`, unlike the `Auto` wrapper, does **not** populate `nBandCount`/`panSrcBands`/`panDstBands` and fails validation with "no bands configured" if you don't.

**`StretchMode::Automatic` is the default, and it earns its complexity.** The first version defaulted to a 2-98 percentile stretch, which is right for a DEM and wrong for a basemap: zooming into the Natural Earth shaded relief produced garish oversaturated colour, because the image's colours were already correct and the stretch was re-mapping them to whatever happened to be in view. Caught by looking at it, not by a test. `Automatic` now resolves per file - 8-bit bands tagged red/green/blue are left alone, everything else gets the percentile stretch. Neither fixed default is right for both cases, so the file decides.

**The image is drawn by its own extent, not the viewport's.** A `RasterImage` carries the ground it actually covers (snapped outward to whole pixels, and clipped to the overlap when the window hangs off the edge). That one choice is what makes asynchronous reads behave: after a pan the previous image still lands on the right ground, merely offset and soft, instead of sliding with the camera. The viewer re-reads only once the view has moved by 25% of itself, so a drag doesn't queue a read per frame.

**Threading:** reads happen on a dedicated `rasterThread_` and come back through `PostMessage`, the same handoff `loadInBackground` uses - `map_` stays the UI thread's alone. But identify samples pixels on the UI thread while that read is in flight, and a `GDALDataset` is not safe for concurrent access, so `RasterSource` serialises both behind a `std::mutex`. Contention is negligible: one is rare, the other already I/O-bound.

**Test data:** the unit tests generate small synthetic GeoTIFFs in-process and delete them again, so the suite stays self-contained with no committed binary. `scripts/fetch-raster.ps1` fetches the real Natural Earth raster for looking at. A wrinkle worth noting: that helper drives GDAL directly to *write*, which Core never does, so it can't use `ensureGdalPlatformSetup` and has to set `PROJ_DATA` itself - otherwise a green test run prints "Cannot find proj.db" to stderr, which is exactly how real errors get missed.

Verified: 75 tests pass; golden image byte-exact; the Natural Earth raster warps correctly to Web Mercator with Antarctica clamped; a raster basemap composites correctly under vector borders with transparent fill; identify returns both a country and the pixel values beneath it; and zooming 20 steps into the live viewer resolves full terrain detail rather than blurring, confirming the re-read path end to end.

## 2026-08-26 — Phase 12 interop: MSBuild owns the managed tree, and WRL cannot cross into it

`Cartograph.Interop` exists: a C++/CLI assembly wrapping Core for .NET, plus `Cartograph.Interop.Tests`, a C# console suite of 99 boundary checks. No logic moved into it, and Core gained exactly one line of public API (`Stylesheet::featureCount`).

**The build is split: CMake owns native, MSBuild owns managed.** Two constraints forced this and neither is negotiable. CMake's `COMMON_LANGUAGE_RUNTIME` is *"only evaluated [by] Visual Studio Generators"* and every preset here is Ninja; and CMake cannot build a WPF project at all, which Phase 13 needs. So the choice was never "avoid MSBuild", only "when". Three options were weighed with the user: a second Visual-Studio-generator preset (rejected — two configure trees of the same native code, free to drift, with `ctest` still only running against one), forcing `/clr` flags onto a Ninja target by hand (rejected — it works, I checked, but it is unsupported by CMake, needs machine-dependent .NET ref-pack discovery at configure time, and still leaves Phase 13 needing MSBuild anyway), and the split adopted here. Paying the cost once, at the boundary where it permanently belongs, beat paying it twice.

**The link line is generated, not transcribed.** `cartograph-native.props` is emitted by `file(GENERATE)` from the real target graph into each build directory, and the `.vcxproj` imports the one matching its configuration. This is the part that would otherwise rot: the debug tree links `gdald.lib`/`proj_d.lib` and the release tree `gdal.lib`/`proj.lib`, a distinction nobody would remember to maintain by hand, and the first dependency Core gains would silently break a hand-written copy. The props file also exports `CartographNativeBinDir`, so the managed projects copy their runtime from the directory vcpkg's applocal step already populated with GDAL/PROJ/GEOS's whole transitive closure rather than recomputing it.

**`<wrl/client.h>` refuses to compile under `/clr` — a Windows SDK `#error`, not a warning.** Core's `render/renderer.h` includes it, because `Renderer::render` returns a `ComPtr<IWICBitmap>`. Since `errors.h` needs `render::RenderError`, that contamination reached *every* managed translation unit in the assembly on the first build attempt. The fix is `render_bridge.cpp`, the one file here compiled unmanaged (`CompileAsManaged=false`), and the only file allowed to include that header. Core was deliberately **not** restructured to suit C++/CLI: returning a `ComPtr` is right for the native callers that outnumber this one, and the accommodation belongs on the interop side. The single thing that has to cross back out is the error type, since managed code cannot name `RenderError` without the poisoned header — hence `cartograph_bridge::RenderFailure`, which carries the message verbatim. Core's other four exception types are all declared in wrl-free headers and pass through untranslated.

**Layers are handles (owner + index), not pointers.** `Map::setDisplayCrs` replaces every layer wholesale by re-reading the sources, so a cached native pointer would dangle across it. An index does not, because the reprojected map has the same layers in the same order — and every access re-resolves and bounds-checks, so the worst a stale handle can do is throw. This is also the shape Phase 16's mutable model will want. A test holds a handle across a reprojection and asserts it still resolves, with visibility and opacity intact.

**Exception translation is the load-bearing part.** A native exception unwinding into managed code takes the process down; there is no partial credit. Every public entry point is wrapped, and the managed hierarchy mirrors Core's one-for-one rather than collapsing to one type — a shell has to tell "that file isn't a dataset" from "your style file has a typo" without parsing message strings. The catch chain is spelled out as a macro rather than routed through a shared `[[noreturn]]` helper, so the compiler can still see that every path returns or throws.

**Strings cross as UTF-8, explicitly, in both directions.** `msclr::interop::marshal_as<std::string>` is the obvious-looking choice and it encodes with the process ANSI code page, which turns any non-ASCII path or attribute into question marks. GDAL hands Core UTF-8 and expects it back. The fixture carries country names in fifteen scripts, so the test asserts Fiji's `NAME_JA` arrives as `フィジー` and its `NAME_EL` as `Φίτζι` — a check that fails loudly the moment someone "simplifies" the conversion.

**Rendering exposed is the one-shot path only.** `Renderer.Render` returns premultiplied BGRA, which is byte-for-byte WPF's `PixelFormats.Pbgra32`, so a shell can hand it to `WriteableBitmap` with no conversion — that is why the type is shaped that way rather than more prettily. It wraps `Renderer::render`, i.e. `drawMap`: unculled, unbatched, serial, and permanently untouched by performance work so the golden-image test can never be perturbed. `drawMapCulled` needs a live `ID2D1HwndRenderTarget`, so it belongs with the hosted map surface in Phase 13, not here.

**Toolchain notes worth not rediscovering.** `vswhere -requires Microsoft.VisualStudio.Component.VC.CLI.Support` reports nothing on this machine and is a **false negative** — `/clr:netcore` compiles and links fine; verified before writing any code by building a mixed assembly by hand and confirming its CLR header. `ijwhost.lib` comes from the .NET SDK host pack, not from Visual Studio. In the `.vcxproj`: without `VCProjectVersion`/`PlatformToolset` the default is v100 and the build asks for Visual Studio 2010; `/clr` is incompatible with `/RTC1`, `/JMC`, `/ZI` and `/GL`, all of which are configuration defaults, so all four are pinned off. And a `Reference` to the interop assembly from the C# tests must stay `Private=true` even though the file already sits in the output directory — `Private=false` omits it from `deps.json`, and a .NET app resolves through that rather than by probing its own folder, so it builds clean and dies at startup.

**Test suite is hand-rolled, with no NuGet dependency.** There is still no CI, so `ctest` plus this is the whole gate; a managed suite needing a package restore is one that fails on a fresh clone with no network for reasons unrelated to the code. The assert harness is thirty lines.

**One Core discrepancy found and deliberately not fixed here.** `Map::open` on a path that is neither vector nor raster throws `RasterError`, not `DatasetOpenError` — `addPath` catches the vector failure, discards it, and lets the raster one escape. Both `map.h`'s docstring ("Throws `DatasetOpenError` if a path can't be read either way") and the comment directly above `addPath` ("the vector error is the one reported if both fail") say otherwise, so the code contradicts its own contract in two places. Fixing it properly means distinguishing "not a raster at all" from "is a raster but failed to warp" — the comment explicitly wants the latter to keep surfacing as `RasterError` — which needs a new error type in Core and is Phase 11's territory, not Phase 12's. Left alone and recorded; the boundary test asserts the base `CartographException` so it pins this assembly's guarantee rather than Core's open.

Verified: 75 native tests pass and the golden image is still byte-exact; 99 managed boundary checks pass in **both** Debug and Release, which is what confirms the generated per-configuration props file actually works rather than merely looking right.
